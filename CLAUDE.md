# Decker — CLAUDE.md

## Project overview

**Decker** is a Linux application for Elgato Stream Deck hardware. The architecture has three components in the same repo:

- **Server monitor** (`src/decker/server/monitor.py`) — the process launched by `poe server`. Starts the server subprocess, then polls it continuously for health (RPyC heartbeat) and memory usage. If the server fails to respond or exceeds the memory limit (1 GiB), the monitor stops it and restarts it automatically.
- **Server** (`src/decker/server/`) — handles hardware communication via `python-elgato-streamdeck`. Runs **headlessly** as a separate subprocess (RPyC on port 18861), supports multiple simultaneous clients. Started and supervised exclusively by the server monitor. Exposed RPC commands are discoverable through `commands` (devices, pages, keys, plugins, icon packs, settings, `heartbeat`, `status`, `stop`, `server_settings`, `server_settings_set`). There is no `start` RPC — the server is already running when clients connect. Key faces may be animated GIFs, played by a per-device adaptive writer in `src/decker/animation/` (see `docs/superpowers/specs/2026-11-17-animated-key-faces-design.md`). The server also detects the focused window with no client running (`src/decker/server/windows/` backends behind `WindowBackend`, `WindowWatcher`, `AppRuleEngine`) and switches profiles from per-device ordered rules plus a default rule (`AppRuleStore`/`AppRuleController`; `app_rule*`, `app_default_rule_set`, `window_detection_status`, `window_pick` RPCs; `app_rules_changed`, `window_detection_changed`, `window_focused`, `window_picked` events); see `docs/app-profile-switching.md`. It also runs a per-device screensaver with no client (`src/decker/server/screensaver/`: `ScreensaverEngine` schedules idle activation and waking, `ScreensaverController` validates and announces, `ScreensaverStore` persists, `compose` cuts the picture into per-key faces; `screensaver_get`/`screensaver_set`/`screensaver_activate`/`screensaver_deactivate`/`screensaver_preview` RPCs (the settings Device tab no longer has an Activate/Wake button); `screensaver_changed` and `screensaver_settings_changed` events); see `docs/screensaver.md`.
- **Client / UI** (`src/decker/client/`) — a PyQt6 GUI built on a `QStackedWidget` view system. `MainWindow` (`window.py`) registers its views (`DashboardView`, `DeviceView`, `ErrorView`, plus the `ReconnectWaitingOverlay` shown while disconnected) keyed by `ViewName(StrEnum)` and is the sole writer to the `AppContext` singleton. The profile selector's "Edit profile…" entry opens a combined `ProfilesDialog` (profiles and app rules) with a Window Spy. Settings live in a separate non-modal `SettingsDialog` (`widgets/settings_dialog.py`). Its Plugins tab (`widgets/plugins_tab.py`) lists plugins that failed to load or run (from `plugins_load_failures` and `plugin_failed` events) grayed among the installed ones, with the error as the row's tooltip and Uninstall/Update still available (a folder with no valid manifest shows by folder name; there is no separate failures list). Its Device tab (`widgets/screensaver_panel.py`) edits a device's brightness and screensaver live, outside the dialog's Apply button. `ConnectionManager` owns the RPyC connection on a background thread (no Qt imports) and pushes `AppEvent`s (`ServerConnectedEvent`, `ServerDisconnectedEvent`, `DeviceListUpdatedEvent`, `KeyEvent`) through a thread-safe `EventHub`, which `MainWindow` drains on a 16 ms `QTimer` and routes to the active view.
- **Plugins** (`src/decker/plugin/`, `src/decker/server/plugins.py`, `decker_plugin_sdk`) — cards, actions, icon packs and variables come from installed plugins, never from server code. A **card** is what a key shows (the picker lists cards) and only draws: it keeps raw `key_down`/`key_up`, and what a key does is its three **bindings** (`press`, `double_press`, `long_press`), each an action plus arguments or Do Nothing (`src/decker/plugin/bindings.py`: manifest defaults on the card, the key's stored `bindings` in `KeyAssignmentStore`, `effective_bindings` merging them, so a gesture the user never touched follows the manifest and a stored `{"action": "com.decker.core.nothing"}` is a deliberate Do Nothing; `key_update_bindings` RPC; `PluginManager` registers on the key's recognizer only gestures bound to an installed action it may use, a foreign plugin-scoped or missing action acts as Do Nothing, and cards see their bindings, with page/profile and template arguments resolved like settings, in `will_appear`/`settings_changed`). An **action** (`contributes.actions`, `scope` `"global"` or `"plugin"`, default `"plugin"`; optional `returns` text) is a headless unit of work with arguments that always runs in its plugin's process (`ActionRunner`, `src/decker/server/actions.py`: `run_action`/`action_result` round trip, `ActionCall` in `action_calls.py`; the value, at most `MAX_VALUE_BYTES` = 1 MiB encoded, goes back to the caller and is discarded for gestures; failures are announced as the `action_failed` event). Plugin code calls actions with SDK `call_action`/`call_action_async` (`call_action`/`call_result`; own actions of either scope, other plugins' global ones; `MAX_DEPTH` 8 counted by the server from the `chain` the caller forwards, so a raw-protocol plugin that omits `chain` starts a new chain at the `depth` it sends (0 if none); `call_action(timeout=None)` lets the server use the called action's manifest `timeout`, else the default 30 s; an explicit timeout overrides it; both are capped at `MAX_CALL_TIMEOUT_S` 300, and a manifest `timeout` is an int of 1-300 s; a nested call is capped by its caller's own remaining time, found through the `parent` request id the caller forwards; a chain from a card carries its device, and while a `run_action` with a device is in flight its plugin may send `switch_page`/`switch_profile` without `context`, which the SDK exposes as `ctx.switch_page`/`go_to_page`/`switch_profile` on the context); the action function takes an `ActionCallContext` (`args`, `input`, `called_at`, `caller`, `card`, `device_id`) and a `CardProxy` (`OwnCardProxy` for the plugin's own cards) exposes the key, and a foreign plugin may touch a card only while the `run_action` that carried it is in flight (`ActionRunner.may_touch`, `_FOREIGN_EVENTS` in `server/plugins.py`: `set_image`, navigation, `show_ok`/`show_alert`, `get_image`; config writes are always refused). Cards paint with the SDK canvas (`decker_plugin_sdk._canvas`: `canvas.paint()` double buffer with a counting lock, a frame ticker sending at most 2 frames per ~33 ms tick to stay under the 100 msg/s flood limit, `on_paint`, `queue_paint`; `get_image`/`image_result` fetch another plugin's key image; the server records `last_paint`; Pillow is imported lazily and the plugin lists it in `requirements`). Decker ships two built-in plugins (`src/decker/builtin_plugins/`; they cannot be uninstalled): Blank (one static card, Blank; Page Name and Page Count moved to the Pages plugin as presets, and a stored Blank pagename/pagecount key loads empty) and Core (four actions: Do Nothing, `com.decker.core.nothing`, the only action the server handles itself and never dispatches, so its gesture is never registered; and HTTP Request, Delay `com.decker.core.delay` (`seconds` 0-60, manifest `timeout` 65) and Sequence `com.decker.core.sequence` (`step_1`..`step_10` actions with arguments, `stop_on_error`, manifest `timeout` 300), which run in the Core process, `builtin_plugins/com.decker.core/plugin.py`; HTTP Request returns `{"status", "body"}` with a 1 MiB result fit and the request timeout clamped to 25 s; Core also contributes presets `com.decker.core.preset-httprequest`/`-delay`/`-sequence`). A built-in plugin with a `runtime` runs on `sys.executable` and the staged SDK with no uv environment (`launch_command(..., builtin=True)`), supervised and lazily started like any plugin. Run Action, Switch (`slots`) and card presets (`card`/`action`/`action_settings`/`behavior`) were removed with format 3; a stored key naming a retired card loads empty. A **preset** (`contributes.presets[]`; `PresetSpec`; `PluginManager.list_presets`, RPC `plugins_presets_list`) is a Blank card plus a name, a picker `icon`, `appearance` and `bindings`: it may bind only global actions or Do Nothing (binding its own plugin-scoped action is a manifest error), declares no `settings`/`states`/`static`/`gestures`, needs no `runtime`, and its plugin must declare a `decker` constraint (`>=0.8`); `appearance.icon.ref` must be a ref (preset `icon` is only the picker thumbnail) and the key title defaults to the preset name. `key_assign_preset` assigns Blank with the preset's bindings and appearance in one step; a dropped key is a plain Blank key with no link to the preset. Unstyled SVG key icons draw white. The client's picker (`widgets/sidebar.py`) is a single Cards tab (icon `images.svg`) that lists cards and presets under their plugin; the Actions tab and `tasks.svg` are gone. The card editor keeps the preview, Save and appearance rows on top and splits the rest into four tabs: Card (`fas:image`, the settings form; hidden when the card has no settings, or kept with a "This card has no settings" hint if no gesture tab is visible either), Press (`fas:caret-right`), Double Press (`fas:caret-square-right`) and Long Press (`fas:hourglass`), the gesture tabs hidden when the card has no bindings model; a tab's text gets a trailing ` *` when modified (Card: a setting differs from its schema default; gesture tabs: the effective binding differs from the manifest default); each gesture tab holds an `Action:` dropdown from `action_edit.py` (ordered Do Nothing, the card's own plugin's actions (either scope), Built-in = Core's HTTP Request/Delay/Sequence, Global = other plugins' global actions each under its plugin sub-header), a ↺ reset-to-default button and that action's argument form; so plugin-scoped actions are reachable only from their card's gesture dropdowns, and global actions also through presets; `key_update_settings` and `key_update_bindings` return `{"ok", "errors": {...}}` (strict validation, nothing saved on errors) and the client shows the errors inline. Counter, Pages and Profiles come from the default repository. Text fields may opt in to `{page_name}`/`{page_index}`/`{page_count}`/`{current_profile}`/`{profile_id}` templates (`template: true`), `page` and `profile` settings types are resolved by the server, and plugins switch pages and profiles with `switch_page`/`switch_profile`; a `choice` setting may declare `options_source`, whose options the plugin supplies when the form opens (`plugin_options` RPC, shown as `plugin.options`, answered by the owner of the schema being edited, so an action's source comes from the action's plugin; `OptionsRunner` asks the plugin with `get_options`/`options_result`, 5 s; the SDK answers with `@options`; the client's `DynamicChoiceEdit` is an editable dropdown that keeps an unlisted stored value; see `docs/plugins/settings-schema.md`). Plugins can also export global **variables** (manifest `contributes.variables`, `name` or `pattern`; `VariableStore` in `server/variables.py`, `VariableRunner` in `server/variable_runner.py`; values come from SDK `@variable` getters, which the server asks with `get_variable` and caches; events added in protocol 2: `register_variable`/`unregister_variable`/`variable_updated`/`variable_value` and `get_variable`/`variables_changed`). Key text templates expand them as `{name}` (page and profile variables win; a declared but unset variable expands to an empty string), and the `variables_list` RPC lists them with owner and value. A plugin that declares variables is the only kind started with the server and kept running (SDK `@init`/`@main` hooks; see `docs/plugins/sdk-quickstart.md`). Plugins can read and set a deck's brightness (SDK `get_deck_brightness`/`set_deck_brightness`, protocol events `get_deck_brightness`/`set_deck_brightness`/`deck_brightness_changed`; clamped to 1-100 and stored as the screensaver's normal `brightness`; `deck_brightness_changed` goes to every running plugin; no throttle beyond the 100 msg/s flood limit) and learn of device hotplug (`device_connected` on every open and `device_disconnected` on close; SDK `connected_devices()`, `on_device_connected`/`on_device_disconnected`, synchronous hooks). The client has an About dialog (`widgets/about_dialog.py`, opened from `MainWindow`, showing client and server versions). Each plugin runs **out of process** (one child per plugin, JSON over stdin/stdout) and is supervised with restart and a watchdog; a crashing plugin cannot take the server down. Plugins are written against the `decker_plugin_sdk` package and shipped as `.deckerplugin` packages whose `manifest.json` declares `format: 3` (formats 1 and 2 are refused, `PROTOCOL_VERSION` 5, Decker 0.8.0; manifests declare `"decker": ">=0.8"` when they use presets, `">=0.7"` otherwise) and `contributes` (`cards`, `actions`, `icon_packs`, `variables`, `presets`). Settings fields may declare validation rules `required`, `pattern` (`re.fullmatch`, compiled at manifest load), `min_length` and `max_length`, checked by `validate_settings`/strict `apply_schema`. Each plugin gets its own uv environment. Settings forms are generated by the client from the manifest's schemas, and Decker draws the key background and title (the `background` appearance setting is nested, `{"type": "none"|"color"|"image", "color", "image": {"ref"}}`, with the image picked from the image library; legacy bare colour strings fold on read; see `docs/key-backgrounds.md`; users can also set a per-key `icon` appearance override, which replaces whatever the action or plugin would show on the key (Clear icon restores it); the editor's live preview comes from the `key_preview` RPC, which composes a draft without saving); plugins supply the key image via `set_image` and may supply a fallback title via `set_title`. The `plugin_install`/`plugin_uninstall` RPCs, and `icon_import`/`icon_delete` (which add to and remove from the `decker.user` User icon pack, whose icons are referenced as `user:<id>`, resolved to the file by `UserIcons.resolve`; `pack:decker.user/<file>` still reads), are restricted to loopback clients unless `server.allow_remote_plugin_install` is set. Icon packs are served over RPC (`iconpacks_list`, `iconpack_icons`, `iconpack_icon`); the client's image library (the picker) browses them remotely and reads no local pack folders; its tree is All Images, User, Built-In, System Icons, then plugins alphabetically, and a thumbnail's GIF/SVG badge sits top right while a User image's delete badge sits bottom right. Decker also serves the server's freedesktop icon theme as ten virtual packs `decker.system.<category>` (Actions, Applications, Categories, Devices, Emblems, Emotes, Mimetypes, Places, Status, Other; `src/decker/asset/systemicons.py`), shown as "System Icons" in the library (Linux-only: hidden on Windows and macOS); the theme is `icons.system_theme` or the desktop's current one, and the `decker.system.` pack id prefix is reserved. Font Awesome Free 7.3.1 ships inside Decker (`src/decker/assets/fontawesome/`, `src/decker/asset/builtinicons.py`) as three virtual packs `decker.builtin.fontawesome.{brands,regular,solid}` under the picker node "Built-In", referenced as `fab:<name>`/`far:<name>`/`fas:<name>` (`parse_icon_ref`/`make_icon_ref` in `common/icon_ref.py`, so every consumer accepts them; manifest `icon` fields read them through `plugin.icons.read_icon`); the `decker.builtin.` pack id prefix is reserved. Plugins find the bundled DejaVu fonts through `decker_plugin_sdk.fonts.font_path` and the `DECKER_FONT_DIR` env var set in `launch_env`. Key fonts resolve via `fc-match`, then an index of the OS font folders, then the bundled DejaVu Sans, and the client registers the bundled fonts with Qt. The monitor sets a stop event so the server's normal shutdown, including stopping plugin processes, runs on every OS; plugins rely on stdin EOF only if the `terminate()`/`kill()` fallback is reached on Windows (where terminate is a hard kill); Windows has no process-group semantics here, so helpers left by an executable plugin after its leader exits are not cleaned up (follow-up: Job Objects with `KILL_ON_JOB_CLOSE`). See `docs/platform-support.md`. Plugin repositories (JSON index format v1, `plugin.repositories` / `plugin.update_check` config) are fetched, cached under `~/.decker/repositories/` and checked for updates by the server (`src/decker/plugin/repository_index.py`, `server/repositories.py`, `server/update_checker.py`); `repositories_check` runs in the background and ends with the `repositories_check_finished` event (network fetches never hold the store lock and have total deadlines); the server pushes `plugin_updates_available` and installs from a repository through the normal installer (`plugin_install_from_repository`). Adding/removing repositories, changing the schedule and installing from a repository are loopback-gated like `plugin_install`. See `docs/plugins/repositories.md`.
- **CLI client** (`src/decker/cli/`) — a terminal client (`poe cli <command>`) that introspects the server's live RPC surface via `commands()` — no hardcoded command list.

Early alpha; the hardware integration layer and server/client separation are the current focus.

## Server fault-tolerance model

`poe server` launches the **server monitor**, not the server directly. The monitor:

1. Spawns the server as a child process.
2. Periodically sends an RPyC heartbeat; a non-response counts as a failed check.
3. Periodically samples the server process's RSS memory via `psutil` (`decker.common.processes.rss_bytes`).
4. If consecutive failed heartbeats reach the threshold **or** RSS exceeds **1 GiB**, the monitor stops the child and restarts it. Stopping asks the server to shut down (a shared stop event, so the normal shutdown runs on every OS), waits `server.stop_timeout` seconds (default 10), then terminates and finally kills it.
5. If the server exits with **code 0** (triggered by the `stop` RPC), the monitor treats it as an intentional shutdown and exits cleanly — it does **not** restart. Any non-zero exit code is treated as a crash and triggers a restart. Exit code **75** (`RESTART_EXIT_CODE`, `server/reconfigure.py`) means a client changed settings (port, memory limit, image size limit): the monitor re-reads the config, rebuilds its server handle and, if the new server does not answer within `server.apply_timeout`, rolls back to the last good settings and records `server.last_apply_error`. Who may change settings is `--allow-client-reconfiguration [hosts]` (absent: nobody; bare: any client; hosts: those plus loopback; never persisted); the host is client-side only. See `docs/server-reconfiguration.md`.
6. If starting the new child fails, the restart is retried on the next check round; there is no backoff or maximum restart count yet.

The server itself has no self-healing logic — fault tolerance is entirely the monitor's responsibility.

## Running the project

```bash
# Run the server (normal mode)
poe server

# Run the GUI client
poe client

# Run the CLI client
poe cli list            # list all server commands
poe cli status          # call a specific command
poe cli stop            # gracefully stop the server (monitor exits too)
```

System dependencies required: `libhidapi` (`sudo pacman -S hidapi` on Arch/Manjaro) and `uv` (builds per-plugin environments). Plugin author docs live in `docs/plugins/`; keep them in sync with protocol and manifest changes.

## Quality gates — run all before marking work done

```bash
poe format   # isort + black (auto-fixes; run first)
poe mypy     # type checking
poe pylint   # linting (must score ≥ 9.0)
poe test     # pytest with coverage (target ≥ 85%)
```

Run `format` before the others; it changes files that the linter then re-checks.

Decker supports Windows and macOS, and CI type-checks for them too (`mypy --platform win32 .` and `mypy --platform darwin .`, besides the default run). Run both before pushing: POSIX-only APIs such as `signal.SIGKILL` or `os.getuid` are errors under `win32` even in code or tests that are skipped there. Use the portable form (`psutil.Process(pid).kill()`), or guard with `sys.platform` in a way mypy understands.

## Code style

- **Formatter**: black (line length 120) + isort (`black` profile). Let the formatter decide; don't fight it.
- **Types**: Always annotate — return types, parameters, and instance attributes — even when mypy doesn't require it.
- **Naming**: `snake_case` for functions/methods/variables/modules, `PascalCase` for classes, `UPPER_CASE` for module-level constants.
- **Docstrings**: Public classes and public functions only. One short line is enough unless the contract is non-obvious. No multi-paragraph docstrings. Private/internal members (`_` prefix) get no docstrings.
- **Comments**: Only when the *why* is non-obvious. Never narrate what the code already says.
- **Method size**: Keep methods under 50 lines. If a method is growing, extract a private helper rather than commenting sections.
- **Max args**: 5 per function/method (pylint enforces this).

## Testing

- Framework: `pytest` with `assertpy` for assertions.
- Target: **≥ 85% coverage** (`poetry run poe test` reports this).
- Test files live in `tests/` mirroring the source layout.
- Pylint docstring requirements are relaxed in tests (configured in `pyproject.toml`).
- Do not mock the database or other infrastructure unless absolutely necessary — prefer integration-style tests against real components.

## Architecture constraints

- `poe server` launches the monitor, which launches the server — never start the server directly in production.
- The server runs headlessly; it has no GUI of its own. `application.py` exists for potential future use but is not loaded server-side.
- Do not add a `start` RPC to `DeckerService` — the server is already running when clients connect.
- `stop` RPC exits the server with code 0; the monitor interprets code 0 as intentional and stops itself. Never restart on code 0.
- Server and client are separate entry points; keep their modules decoupled.
- Server must support multiple simultaneous clients.
- Waking the screensaver never fires an action (the waking key press and its release are swallowed), and the screensaver never mutates stored page, key or profile state.
- App rule edits never switch the deck (they apply at the next focus change), and the server, not the client, detects focus.
- All hardware interaction goes through the server; the client never talks to hardware directly.
- Fault-tolerance (restart, health checking, memory limiting) lives in the monitor, not in the server.
- Process groups, tree termination and RSS reading are cross-platform and live in `decker.common.processes` (on Windows `adopt` puts a spawned process in a kill-on-close Job Object via the private ctypes module `_winjob` and `kill_tree` terminates the job, reaching helpers of an exited leader; `terminate_tree` and the no-job fallback are a psutil walk that leaves orphans of an exited leader alone, since pids are recycled; POSIX uses `os.killpg`); use it instead of `os.killpg`, `start_new_session` or `/proc`.
- Each device has profiles (integer ids, lowest unused first, reused after deletion; id 0 is "Default"), and each profile owns its pages. Key assignments, key images and labels are stored per page (`PageStore`, `pages.py`; page ids are unique per device, so a page identifies its profile). Each device shows one active profile and page; only that page's cards are live, and `PageController` (`page_controller.py`) owns every page and profile switch. Key RPCs take a `page_id`. `key_move`/`key_copy` re-key or copy a key's assignment within a page (a move keeps the instance's context id; a copy gets a new one). In the client grid a click selects a key for editing, its hover play-circle icon (top right) runs it (click = press, hold = long press), its hover red delete icon (bottom right, keys with a card only) clears it with `key_unassign` after a confirmation, and dragging a key onto another moves it (Ctrl: copies it).
- Device IDs are stable 8-char CRC-32 hex strings derived from the device serial number. The selected device is persisted as `client.default_device` in the user config layer.
- Configuration is YAML-based; use `flatten-dict` for nested config operations.
- RPyC is the IPC layer between server and client.

## Platform support

Five tiers, in priority order: (1) Linux Arch/Manjaro/Plasma/Wayland, (2) Linux Ubuntu/Debian/Fedora/GNOME, (3) Linux other (90-100%), (4) Windows (75%+), (5) macOS (75%+). Every feature and plugin must target them. Update the platform table in `README.md` (and the plugins repo's README table); tiers and rules stay in `docs/platform-support.md` in the same change; plugins declare `platforms`/`linux` in the manifest.
